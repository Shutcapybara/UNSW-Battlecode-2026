## The brief

You are not given a hypothesis. You are given a bot (Ares V06, atlas off — or V05 if R-1's step 0 has already
shown V06 does not generalise; check `claude/r1-status.md`), a yardstick, and a gate. **Make the bot better on the
yardstick, one change at a time, and keep only what passes the gate.** This is the fishtest model: the value of
the lane is the number of accepted patches, not the size of any one idea.

## The loop (repeat until stopped)

1. Pick one mechanism. Sources, in the order they have paid so far: the death ledger (C1-C: trapped, newborn,
   portal-exit, crowd — these are Tyr-lineage leaks and Ares *is* the Tyr lineage, so they are live here even though
   C1-F could not see them on the chassis); the retention gap in the BENCHMARKS chart (zoo length at r100 is
   0.87–1.00 of the field median against 1.26 for winners; we eat like winners and don't keep it); the C1-E
   efficiency ratio (top-30 eat 8.5 pearls per 100 dragon-turns at 11.7 moves per pearl); the temporal ideas in
   `claude/ten-day-plan-2026-09-29.md` §S-1…S-5 (EW densities, action memory, crown consensus, scout splits,
   clock as a continuous input); anything you see in a replay. One mechanism, one directory, one `CANDIDATE.toml`
   line stating the mechanism and the expected sign on a named metric **before** you run it.
2. Implement it as a **switch** in your copy (`params.hpp`), default on in the candidate, so the parent is
   reproducible from the same source. Golden-harness the parent first (`tools/cx/golden.py replay … --all`) so
   you know the copy has parity before the change; note the fingerprint.
3. CPU probe on the four dense fixtures with `arena.py --sandbox`; a change that raises the per-turn max above
   the level R-1 has published as safe (until then: 30 M) is rejected on that alone.
4. z1 panel, seed 1, both seats, atlas off; score with `tools.analysis.features.benchmarks`; then the
   generalisation panel. If the pool result is inside the resolution table in BENCHMARKS §"How to use it", add
   seed 2 before deciding.
5. Accept only on the BENCHMARKS gate (economy mean +0.05 with r100 dragons/length not down; no hygiene rate up
   >10 %; panel win rate not down) **and** a non-negative result on the generalisation panel. A change that passes
   the pool and fails the panel has learned the ten maps; reject it and say so. A hygiene improvement with a flat
   economy is a **hold**, not an accept: keep the switch off, log it, and re-test it stacked on the next accepted
   economy change.
6. Accepted → the new base (`<lane>-<nn>`), one commit, one row in the running table. Rejected → one row in the
   running table with the number that killed it. Either way the switch stays in the source.

## What the lane may not do

- Change two mechanisms in one version, or tune three parameters and call it one change. A parameter sweep is
  one mechanism only if the parameter already exists and you report the whole sweep.
- Read a map name, hash, atlas index or anything that identifies a map. Structure the bot can measure — yes.
- Optimise a tier-3 (relative) metric or panel win rate directly; they are guards.
- Pick opponents. The panel is fixed (`run_panel.ZOO`, ten live maps, `maps/new/`, `maps/var`).
- Touch Ares, Tyr, Anna, `cx-*`, R-1/R-3/R-5 directories, or the other open lane. Read them freely; copy what
  you use into your own tree and say where it came from.

## Reporting

`claude/<lane>-status.md` updated after every version with the running table (version, mechanism, pool delta,
panel delta, CPU max, verdict, one line of why). `docs/findings/2026-09-3x-<lane>-lane.md` at every fifth version
or when the lead asks: what was tried, what was accepted, what the accepted stack adds up to against the base on
both panels, and which *kinds* of mechanism paid (that is the information the director needs to redirect the
directed tasks). Every accepted version gets a `CANDIDATE.toml` (`language = "c++"`, lineage `<lane>`,
`lineage_parent` = previous accepted) and a line saying it is ready for `register.json`. Do not register.

The two lanes (`ra`, `rg`) run the same brief from the same base. Diversity is the point; do not coordinate
mechanism choice with the other lane, but do read its status file before picking, and do not repeat a rejection
it has already logged unless you can say what is different.
