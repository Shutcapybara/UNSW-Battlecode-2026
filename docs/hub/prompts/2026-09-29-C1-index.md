## Why this phase exists

Every live loss is decided before round 100 (17 opposing units to our 11 at r100; behind on total by r100 in 68 of
80 losses). The judge gives 100 M CPU points per dragon per turn and kills a dragon that exhausts them; a round parse
costs the Python helper ~10 M, a 32×32 flood fill 19 M in Python and 0.3 M in C++. Our Python bots are at or near
that ceiling (9508: cap in half its games, ~7.7 timeout deaths a game). So the next phase is C++, early game only:
build the chassis, spend the compute on route finding and bed assignment, close the efficiency leaks, stop dying
in portals. Late game is out of scope until the opening is fixed.

**Pace cannot be forced.** The P1 probe (29 Sep) showed that pushing production by schedule neither reaches the
field's curve nor wins when it does. The gap is efficiency — pearls per dragon-turn, moves per pearl, dragons lost
before they pay for themselves — so C1-B (routing) and C1-C (the ledger and its leaks) are the centre of the phase,
and no task sweeps split timing for its own sake.

## Shared rules (apply to every C1 task; each prompt repeats only what differs)

- **Identity and boundaries.** Lineage prefix `cx`. Directories `REPO/bots/cx-<task><nn>-<slug>`; never overwrite a
  version; never edit another lineage's directory. Work in `git worktree add ../wt-cx-<task> -b cx/<task>`. Commit
  your bot directory, findings file and run files only. No live actions, no API key, no uploads: the hub does that.
- **Toolkit.** `unswbc` 1.2.2 in a scratch venv (`python3 -m venv ~/.venvs/bc122 && ~/.venvs/bc122/bin/pip install
  unswbc==1.2.2`). `unswbc init cpp NAME` gives the official `helper.hpp`; `unswbc run MAP BOT_A BOT_B` plays a game;
  `--sandbox` prices instructions exactly as the judge does (100 M points/dragon/turn; a turn over budget kills the
  dragon). Every C1 deliverable reports sandbox p50/p99/max points per turn on Schooltime A, Portals B, Slithery
  Fight A, Trauma B; the gate is zero faults, max < 80 M, p99 < 60 M. `bot.toml`: `language = "c++"`, `include` lists
  the sources. 48 MB per dragon, one thread. The first turn is charged (imports/setup).
- **Protocol.** Protocol 3 (sonar echoes). Read `docs` → IO Protocol and Helper Reference; `bots/fry-v03-portal-
  hunters/hunter.cpp` is an older hand-rolled C++ client worth reading for structure, not copying for protocol.
- **Reference bot.** `bots/yuna-v03-core` (Python, ~2.5k lines; the bot that passed today's screen against the live
  control) is the behavioural reference for the golden harness and the baseline for every ablation.
- **Maps.** `REPO/maps/*.map`; the live pool is ten maps: Portals, Schooltime, Default, Autarky, Trauma, Prisoners
  Dilemma, Slithery Fight, Queen Of Spades, Trophy, Devil. Compact = Portals, Dilemma, Devil, Trophy (where we are
  eliminated). Starting layout is a function of (map, game-id parity): test both sides.
- **Measurement.** Seeded fixtures on the ten live maps × both sides × seeds 1–3 against a fixed local panel
  (`bots/yuna-v03-core`, `bots/fenrir-v18-arrival-ready-beds`, `bots/kazuha-s01-swarm-dissolve`, and every
  `bots/clone-*` present). Report exact pairs (map, side, seed): better/same/worse and the sign-test p, never pooled
  win rates alone. Early-game statistics are the primary outcome: **units at r25/r50/r100, total length at r100/r250,
  first-pearl round, pearls eaten by r100, deaths by cause per 1k dragon-turns (wall/self/ally-body/h2h/portal-step)**.
  `tools/game_stats.py` and `tools/replay_stats/` compute most of these from replays; extend, don't fork.
- **Targets** come from C1-E's table when it lands; until then use the live opponents' medians from A1: units r100
  ≥ 18, total r250 ≥ 60, first pearl by r12 on compact maps.
- **Local ≠ live.** Local numbers select; the hub decides. Every finished bot gets a `CANDIDATE.toml` (copy the
  schema from `bots/kazuha-s01-swarm-dissolve/CANDIDATE.toml`: hypothesis, mechanism, expected_change, activation
  markers, local evidence) and is registered by the director; the hub runs the dev pass (20 games vs 545/752, zero
  faults), the dev screen (3 blocks, 545/752/45) and, if it passes, the field confirmation.
- **Deliverable format.** One findings file `docs/findings/2026-09-3x-<bot>.md`: six lines up front (what was
  built, the number that decides, pairs better/same/worse, sandbox p99/max, what failed, what next), then detail.
  Project status doc `claude/<task>-status.md` updated at every stop. Hypotheses carry falsifiers; report which fired.
- **Do not.** Build scouts, density gossip or late-game feeding (all measured negative — S1 §2). Change the
  measurement tools' semantics. Spend more than a third of the time on infrastructure. Optimise against `fry-*`.
