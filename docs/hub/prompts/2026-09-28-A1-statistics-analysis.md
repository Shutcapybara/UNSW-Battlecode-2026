## 0. Your job

Turn the team's accumulated statistics into decisions. Four bodies of data exist and nobody has read them together: ~450 live server games with per-game stage curves, 125k local games across 280 bot versions, four public-replay corpora with byte-exact reconstructions, and the first live-versus-local calibration rows. Produce (a) a **statistics atlas** — one document that says what each dataset can and cannot answer, with the headline numbers; (b) **findings** with falsifiers on the ten questions in §3, in priority order; (c) **code** that makes the recurring parts run inside the hub cycle; (d) a **research list** for the data that does not exist yet (§4), each item with cost and the decision it unlocks. You are an analyst: you do not upload, activate, or touch the API key, and you do not edit other lineages' bots.

## 3. The analyses, in priority order (question → data → method → output → what decision it feeds)

1. **Loss anatomy on the live record.** For every live source with ≥ 20 controlled games (9508, 9663, 8540, 9639, 9980): losses split by `reason`, map class and opponent; median elimination round; longest margin in round-limit losses; stage curves (units r100, total r250, longest r400/r499, ours vs opponent's) for wins vs losses; deaths per 1k turns by cause (wall/self/other-body/h2h) and newborn deaths ≤ 10 rounds; the first stage at which the eventual loser falls behind on total length. Method: per-game rows, opponent- and map-stratified medians, plus a simple survival curve of "our units > 0" by round per map class. Output: one table per source + a two-line diagnosis per source. Decision: whether the next candidates should target opening production (compact eliminations) or late conversion (round-limit longest) — today's evidence says the former (9508: 28 of 51 compact games lost by elimination, units r100 6 vs 15 on open maps).
2. **Candidate-minus-control contrasts.** For every screen block with exact pairs (a01aee66, 8b12ae55, 02356998, 88a5b9be): per-map paired score delta and the stage-profile deltas on the same pairs (units r100, total r250, longest r400, deaths). Method: paired differences on (map, side, opponent submission, layout); report pairs better/worse; never pool unpaired games. Output: "what changed when the outcome changed" for each rejected candidate. Decision: which mechanisms to stop re-testing (the lineage ledger).
3. **Starting-layout assignment.** Each live game records `map_hash` (the starting layout; two values per map). In block ca5af1bf the candidate arm got the opposite layout on all ten maps; in the other two blocks 9/10 and 8/9 matched. Question: is the layout a function of something we control or observe (request order, seed parity, series position, time)? Data: all 447 games' `seed`, `map_hash`, `requested`, `series`, side. Method: contingency tables and a logistic fit of layout on candidate covariates; also inspect the seed → layout mapping (does the same seed give the same layout?). Output: a rule or "random". Decision: fill strategy (alternate arms vs request both layouts deliberately) — fills currently cost up to 6 batches per block.
4. **Live-versus-local transfer.** Extend `tools/hub/calibration.py`: (a) trajectory matching — for a fixed source and map, which local opponent induces the r100/r250/r400 profile closest to what each live opponent (62, 45, 470, 306, 545, 752) induced; (b) toolkit strata — do 1.0.0 native and 1.2.x seeded games give the same stage profile for the same bot pair; (c) map-level disagreement. Data: live stage curves + local comparison-run `stats/*.json` series (the ledger itself has outcomes only). Output: an opponent-proxy table ("live 62 ≈ local X on maps M") and the updated expectation model. Decision: the reference set of the live-pool panel and whether local scores may enter the priority score (rule: paired sign agreement ≥ 70 % on ≥ 10 pairs).
5. **Opponent models for the ladder band.** Our rating is decided by teams within ±8 places (ranks ~68–84 at 12:00 UTC: 853, 241, 45, 481, 473, 133, 187, 30, …). Nobody has profiled them. Data: their public replays (download via `tools/download_team_games.py`, ≤ 60 newest per team, keep version strata) → `tools/team_recon_claude/descriptive.py` fingerprints (units r100/r250, longest r400/r499, split modes, salvage rule, dissolve onset, sonar rate, portal use, elimination timing). Output: a behavioural clustering of the band plus the two dev bots and the three strong teams; a recommendation of six band representatives for clones (the Vibing++ mimic recipe: `experiment_data/team_recon_306_20260927_claude/REPORT.md` §5a) and of which teammate uploads to recover from the API zips as local opponents (every one of our 75 submissions is byte-recoverable). Decision: the local panel's opponent set.
6. **Runtime.** From live games' `cpu_max` and `cpu_recorded == turns`, and from probe logs' per-turn points: distribution of max and p99 by source, map and round window; near-cap turns (> 90 M) and what precedes them (units, sonar, message counts). Cross with the self-audit's public numbers (loki 100 M in every game; gavroche-v32 96.6 M; 9663 97.46 M). Output: a runtime table and the map/round conditions that produce spikes. Decision: the local gate thresholds (80/60 M) and whether Python hosts need a degradation mode before the S1 bots ship.
7. **Sonar audit.** Our Python lines send ~3.9 rays per decision; Vibing++ 2.4; Heartbreaker 4.5 M rays with payload zero. Question: does sonar volume buy anything? Data: live stage `sonar` counts, outcomes, cpu_max; message counts on receipt from probe logs (`NUM_MSGS`). Method: within-source correlation of sonar rate with outcome controlling for map; cost per ray in points. Output: a cost/benefit line per line. Decision: whether the framework's "every packet kind names its consumer" rule should force a cut.
8. **Judge divergence status.** From `claude/jks-self-audit-status.md` §2: replay-drive is exact for games before ~13:00 UTC 27 Sep and ~92 % after; local 1.2.2 does not reproduce it; the difference is message-driven. Task: check whether the live games since then (all of `LIVE`) show the same signature (compare `NUM_MSGS` implied by sonar hits in the replay vs what a re-driven bot would receive), and write the one-game experiment that settles it (a tap build logging raw stdin) for the director to authorise. Decision: whether local metering and replay-drive remain valid evidence for post-change games.
9. **Ranked exposure accounting.** `ranked_exposure` rows: 15 ranked games played by executor uploads (9663, before it was chosen as incumbent) at 06:46 and 08:00 UTC. Compute the Elo impact of testing to date from the series' `eloChangeA/B` (fetch details for completed series via the legacy cache), and estimate the K-factor regime our uploads inherit (fresh-start vs inherited count) from submission timestamps. Decision: the width of the blackout window around even UTC hours after cutover.
10. **Rating-table sanity.** `benchmark_ratings.py`'s "Sparse" top (tidus-t02 86 % on 86 fixtures, fenrir-v18 85 % on 26) versus their live shares (tidus-t02 screen at −0.11 over 9 pairs vs 45; fenrir-v18 0.43 over 123 live games). Output: a minimum-evidence rule for the table (fixtures, opponents, maps) and a shrinkage prior, proposed as a patch to `tools/benchmark_ratings.py`. Decision: whether the campaign table is allowed to order the queue at all.

Method standards for all ten: declare the analysis before looking at outcomes; report effect sizes with intervals and the independence unit; stratify by opponent submission and toolkit version; A-side only unless a B-side sample exists; never count unverified games; treat public replays' missing fields as missing.
